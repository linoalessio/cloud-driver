# Troubleshooting

Real issues encountered running this system, and their actual fixes — kept here so they aren't
rediscovered the hard way a second time.

| Symptom | Cause | Fix |
|---|---|---|
| Server crashes with an out-of-memory error while persisting a large upload | Several full in-memory copies of a file's content existed simultaneously on the persist path (compressed bytes → encoded string → JSON → re-encoded bytes → encrypted) | Fixed: file content is now chunk-encrypted as a stream (O(chunk size), not O(file size)), and a server-mediated upload above 32 MiB never materializes in heap at all — the body lands in a scratch file and checksum/encryption/S3 write all run off it. Below that threshold the in-memory path is kept on purpose (it powers compression and text extraction), so an explicit, sufficiently large `-Xmx` is still required for concurrent mid-size uploads |
| A route silently returns a bare `500` with nothing printed anywhere | Framework request-logging is intentionally silenced, and an unmapped exception on that route wasn't being printed before being translated into a response | Every route's failure-translation path now logs the full exception to the server's own console before responding |
| Uploads succeed but the file can't be opened/downloaded immediately afterward | Under a burst of concurrent uploads, the outbound network probe used to detect "offline" can spuriously report unavailable, silently deferring a real upload into a retry queue instead of persisting it right away | Where the database is co-located with the application server, connectivity is treated as always available rather than probed per upload |
| A freshly uploaded file reports a `0` byte size, or downloading it 404s | The running backend jar predates the code that captures file size/metadata, or predates the download route entirely | Rebuild and redeploy the backend jar — this is a stale-deployment symptom, not a client bug |
| Nothing serves after a release — the process exits during startup with `the extension '<name>' is declared twice`, or the launcher's restart loop repeats the same startup crash every three seconds in a `screen` session with no scrollback | `extensions/` is additive and every jar in it is version-suffixed, so a deploy that did not remove the previous release left two jars declaring the same extension name. Every jar found is registered before anything starts, so the whole process comes up dead, and which of the two jars was reached first depended on filesystem order | Delete the older of the two jars the message names and restart. Deploys now prune the previous release only after the replacement has verified, refuse to upload an extension jar that does not carry the bootstrap jar's version or two jars for the same module, and the launcher refuses to start at all when `extensions/` holds two jars for one module. Extension jars are loaded in file-name order, so the report is the same on every host |
| The whole server crashes on startup with a class-loading error the moment a particular feature module is present | A feature module needs a third-party library nothing else in the process already provides, and feature-module jars only resolve shared classes off the host jar's own classpath | Add that library as a dependency of the main runnable jar itself, so it's present on the shared classpath every feature module falls back to |
| Deleting a large folder tree (or a similar bulk operation) fails with a "too many concurrent streams" error | Each level of a recursive operation independently capped its own concurrency, so the real total concurrency multiplied with tree depth/width instead of ever being bounded | List the whole operation's items first, then run exactly one bounded-concurrency batch over the flattened list |
| A signed-in session stops surviving an app restart, even though it worked minutes earlier | A session token was rotated during use but never re-persisted to local storage, and/or the value being stored contained characters a backing credential store silently mangled on read-back | Persist the session on every token rotation, not only at initial sign-in, and store composite values in a plain-text-safe encoding |
| Extracting/uploading a folder from a cloud-synced location fails with a generic filesystem error | A shallow check only guarantees the top-level picked item is materialized locally, not every nested file several levels down | Recurse with a real per-item existence check, not a resource-value property a given storage provider might not populate |
| A desktop window can be resized down until it effectively disappears | The window had no enforced minimum size | Enforce a floor, but do it through the UI framework's own window-state API — mutating the underlying native window object directly can corrupt rendering across the whole app |
| A share recipient never sees anything shared with them — `GET /files/shared-with-me` answers `404` with `No StoredFile with id shared-with-me`, while the share's *write* side looks perfectly healthy (`POST /files/{id}/share` succeeds and `GET /files/{id}/share` lists the grant back) | Javalin's path matcher does a plain linear scan in registration order and returns the first template that matches — it has no "static segment beats path parameter" precedence. `GET /files/shared-with-me` was registered *after* `GET /files/{id}`, so every request was swallowed by the download handler treating `shared-with-me` as a file id. The 404 is the red herring: sharing itself never broke, only the route table — which is why the grant was visible from the owner's side the whole time | The four single-segment `GET /files/…` routes (`/files/trash`, `/files/shared-with-me`, `/files/shared-by-me/count`, `/files/duplicates`) are now registered *before* `GET /files/{id}` in `DefaultRestFactory#start`. That ordering is load-bearing, not a style choice — a new single-segment literal `GET /files/…` route added below the `{id}` registration is silently dead. The scan runs per verb, and a template only ever matches a path with the same segment count, which is why the `/files/upload-url` and `/files/upload-session` registrations are safe *below* `GET /files/{id}`: the only single-segment one of them is `POST /files/upload-url` and no bare `POST /files/{id}` route exists, while every upload-session route carries at least one segment more than `/files/{id}` can match |
| After a few thousand files are uploaded, browsing the desktop app's file list takes minutes instead of seconds — every folder open and every "Load more" click, not just the first | Each listing call re-listed and re-decrypted *every* row of the type from scratch, and decrypting a row unwraps its data key through AWS KMS — one network round trip per row. A ~2,500-file account therefore paid thousands of KMS calls per listing call (`CloudUserService#listFileSummariesPage`/`ownedFileOwnerships` hit `StoredFileOwnership` on every call) | `EntityDatabaseClient` now keeps a short-TTL snapshot of each type's decrypted `getEntities` result (5 minutes in `FactoryContainer`, dropped immediately on any write to that type), so back-to-back listings share one decrypt pass. `StoredFile` is deliberately excluded (TTL `ZERO`): its rows can still carry a legacy file's full inline content, which must never be pinned in heap for a cache window |
| Boot crash-loops, with `PSQLException: An I/O error occurred… Unexpected packet type: 102` printed against a trivial statement | Boot loads every table's rows into the persistence layer's in-memory entry cache; the JDBC driver additionally buffered each full table before the first row was parsed, so once the largest table outgrew the heap, boot died of `OutOfMemoryError` mid-load — the "packet type" error is only the half-read connection the dying process left in the pool, not the real fault | The persistence layer (`database-driver` ≥ 1.3.14) now discovers table *names* only at boot (no row data) and streams any later full-table load in bounded batches; `-Xmx` was also raised (4g → 6g) and a swapfile added as the kernel-OOM floor — the heap value now lives in `JVM_XMX` in a sibling `start-cloud.env` that `shell/start-cloud.sh` sources (the installer writes it; `6g` is only the launcher's own fallback when no env file is present), and the swapfile is created by the installer's Swap step or `shell/provision-root-server.sh`, never by the launcher — see [requirements.md](requirements.md) §7 |
| The stored-file table balloons with thousands of `thumb_thumb_…_x.jpg.jpg…` files nobody uploaded (~3 GB found in the wild — the very growth behind the boot OOM above) | A generated thumbnail is stored as an ordinary `StoredFile`, whose own INSERT notification fed back into the thumbnail listener — and a thumbnail is a JPEG the image generator supports, so every thumbnail spawned a thumbnail of itself, unbounded | The thumbnails extension now skips any file that is some `FileThumbnail`'s target (with the linking row written *before* the thumbnail file, so the guard is race-free), and prunes accumulated chain/orphan garbage on every start; after a mass prune, `VACUUM FULL` the affected tables to actually return the disk space |
| The server console floods with hundreds of `org.apache.pdfbox … WARNING: Invalid dictionary, found: '…' but expected: '/'` (or "end of the stream is out of range") lines in one burst | Someone uploaded a corrupt-but-recoverable PDF; PDFBox's lenient parser logs one JUL WARNING per damaged object it works around while still rendering a usable thumbnail | The thumbnails extension now raises the `org.apache.pdfbox`/`org.apache.fontbox` loggers to SEVERE at load (holding strong references — JUL levels on unreferenced loggers can be GC'd away); a PDF that genuinely fails to render still logs exactly one per-file WARNING from the extension itself |
| Even with the two fixes above, the process's heap floor still climbed roughly in step with total `StoredFile` content, and the first touch of that table (often early in boot, e.g. the watcher extension registering its `LISTEN`) paid for loading every row at once | `EntityDatabaseClient` created every entity type's `DatabaseSection` with `database-driver`'s default `CacheMode.FULL` — every row loaded on first access and held in the database layer's own cache for the process's lifetime, on top of (and duplicating) `EntityDatabaseClient`'s own already-bounded decrypted cache; harmless for small metadata tables, but `StoredFile` rows can still carry a legacy file's entire inline content | `database-driver` 1.3.15 added per-section `CacheMode`/`SectionConfig` (`FULL`/`LAZY`/`BOUNDED`/`NONE`); `FactoryContainer`'s `SECTION_CONFIG_OVERRIDES` now pins `StoredFile` to `CacheMode.NONE` (every operation pushed straight to Postgres, nothing cached twice) while every other type keeps `FULL` |
| `pytest` in `cloud-driver-multiplatform-python` or `cloud-driver-intelligence` fails at collection with `ModuleNotFoundError: No module named 'cloud_driver_client'` (or `cloud_driver_intelligence`) immediately after a successful `pip install -e ".[dev]"` | Python 3.14 ignores `.pth` files whose name begins with `_`, and hatchling's editable hook (`_editable_impl_*.pth`) is exactly that — so the editable install is invisible to the interpreter even though `pip` reports success | Prefix the run with the source path (`PYTHONPATH=src pytest`), or install non-editable. The permanent fix is the one `cloud-driver-installer` already carries: `pythonpath = ["src", "tests"]` under `[tool.pytest.ini_options]`, which makes a bare `pytest` work on every interpreter |
| Running the GUI installer from an IDE run configuration (i.e. running `__main__.py` as a file) fails while generating credentials with `module 'secrets' has no attribute 'token_hex'` | Running a file *inside* a package puts that package's own directory on `sys.path`, where a module of ours outranks the standard library module of the same name for the whole process. The package's own `secrets.py` (and `profile.py`) then shadowed the real `secrets`/`profile`, so the generators called themselves | The two colliding modules were renamed (`secrets.py` → `credentials.py`, `profile.py` → `profiles.py`) and `cloud_driver_installer/__init__.py` drops its own directory from `sys.path` on import; `tests/test_import_hygiene.py` holds both halves in place, including an assertion that no module beside `__main__` shares a standard-library name |
